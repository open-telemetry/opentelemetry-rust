# Preventing telemetry-induced telemetry with OTLP

OTLP exporters use networking libraries such as `reqwest`, `hyper`, `h2`, and
`tonic`. These libraries can emit their own `tracing` events while exporting
telemetry. If those events are sent through `OpenTelemetryTracingBridge` to the
same OTLP exporter, one export can generate another export repeatedly. This
feedback loop is called **telemetry-induced telemetry**.

The problem usually appears only when dependency logs at `DEBUG` or `TRACE`
are exported. The OTLP examples in this repository avoid it by filtering
transport-library events out of the OpenTelemetry layer.

## Recommended solution: filter transport events

Filtering is the complete solution for almost all applications. It requires no
extra threads, experimental features, or exporter changes.

Apply the filter only to the layer that sends logs to OpenTelemetry. It does not
prevent other layers from receiving the same events. A separate formatting
layer can still print the transport diagnostics locally, which is usually all
that is needed to investigate transport problems.

```rust
use opentelemetry_appender_tracing::layer::OpenTelemetryTracingBridge;
use tracing_subscriber::{layer::SubscriberExt, util::SubscriberInitExt, EnvFilter, Layer};

let otel_filter = EnvFilter::new(
    "info,reqwest=off,hyper=off,h2=off,tonic=off,tower=off,want=off,rustls=off",
);
let otel_layer =
    OpenTelemetryTracingBridge::new(&logger_provider).with_filter(otel_filter);

tracing_subscriber::registry()
    .with(otel_layer)
    // The filter above applies only to `otel_layer`. This layer still receives
    // transport events.
    .with(tracing_subscriber::fmt::layer())
    .init();
```

Use `debug` or `trace` instead of `info` if application logs at those levels
should be exported; keep the transport targets set to `off`. Add the target for
the TLS implementation in use, such as `native_tls` or `tokio_native_tls`.
`hyper=off` also covers targets such as `hyper_util` because target matching
uses prefixes.

If the filter is loaded from `RUST_LOG`, add the transport-specific `off`
directives to the resulting filter. Their target specificity prevents a
setting such as `RUST_LOG=debug` from re-enabling those events for the
OpenTelemetry layer.

See the same pattern, with a shorter target list, in the
[`basic-otlp`](../opentelemetry-otlp/examples/basic-otlp/src/main.rs) and
[`basic-otlp-http`](../opentelemetry-otlp/examples/basic-otlp-http/src/main.rs)
examples.

**Almost all users can stop here.** Needing transport diagnostics for
troubleshooting is not, by itself, a reason to use the more complex solution
below: keep those diagnostics in a local formatting layer instead.

## Very advanced: when filtering is not enough

Filtering removes matching transport events from the OpenTelemetry pipeline
regardless of where they originated. Consider a dedicated exporter runtime
only when the application has the unusual requirement to export `reqwest`,
`hyper`, `h2`, or `tonic` diagnostics from normal application traffic to the
OpenTelemetry backend while excluding diagnostics generated by the OTLP
exporter. A target filter cannot distinguish between those two sources.

This is a very advanced use case. A dedicated runtime provides that selective
isolation, but it adds a thread and runtime resources. Async HTTP additionally
requires experimental processor APIs.

### Dedicated suppressed runtime

The advanced approach runs OTLP exports on a dedicated Tokio runtime whose
threads have OpenTelemetry suppression enabled. Transport events generated on
that runtime are not sent back through OpenTelemetry. The application's normal
runtime remains unsuppressed.

| OTLP transport | Dedicated runtime support |
|---|---|
| HTTP with `reqwest-blocking-client` | No; use filtering or switch to an async client |
| HTTP with `reqwest-client` | Yes |
| HTTP with `hyper-client` | Yes |
| gRPC with `grpc-tonic` | Yes |
| Custom `HttpClient` | Only if its threads and tasks are controlled |

Async HTTP clients must be paired with the experimental async-runtime
processors and readers. They are not compatible with the standard
thread-based processors and readers.

For `grpc-tonic`, the standard processors and readers can be kept. Build the
exporter while the dedicated runtime is entered so the channel's background
tasks are bound to that runtime.

See the compiled
[`telemetry-suppression`](../opentelemetry-otlp/examples/telemetry-suppression/src/main.rs)
example and its
[`Cargo.toml`](../opentelemetry-otlp/examples/telemetry-suppression/Cargo.toml).
The example:

1. Creates a dedicated Tokio runtime.
2. Enables suppression whenever one of its threads starts.
3. Builds the async exporter and processor while that runtime is entered.
4. Shuts down the provider before stopping the runtime.

Important limitations:

- Do not schedule application work on the exporter runtime. Its telemetry is
  intentionally suppressed.
- The experimental async-runtime processors do not enable suppression
  themselves. The runtime hooks in the example are required.
- `reqwest-blocking-client` owns an internal runtime and does not expose a hook
  for enabling suppression there.
- Provider shutdown waits synchronously for processor work. Run it from a
  synchronous shutdown path or use `tokio::task::spawn_blocking`; never run it
  on the exporter runtime itself.
- Context suppression applies to OpenTelemetry logs and traces, not metrics
  recorded directly by a dependency.

For traces, the equivalent processor is
`trace::span_processor_with_async_runtime::BatchSpanProcessor`, enabled by
`experimental_trace_batch_span_processor_with_async_runtime`. For metrics, use
`metrics::periodic_reader_with_async_runtime::PeriodicReader`, enabled by
`experimental_metrics_periodicreader_with_async_runtime`.

## Other logging and tracing integrations

Applications that install `OpenTelemetryLogBridge` directly as the global
`log` logger do not use the `tracing` layer filter shown above. Keep the global
`log` level at `INFO`, or put equivalent target filtering in front of that
bridge. `OpenTelemetryLogBridge` does not currently provide its own per-target
filter.

Some `tracing` spans explicitly request no parent. Those spans may not preserve
context-based suppression when converted through `tracing-opentelemetry`. If
the application exports `tracing` spans this way, retain a target filter on the
OpenTelemetry tracing layer even when using a dedicated runtime.

## Filtering and dependency upgrades

Filtering is intentionally the simple solution, but target names are
implementation details. A dependency upgrade can add or rename targets.
Recheck exported records after upgrading the OTLP exporter or its HTTP, gRPC,
or TLS dependencies.

A likely feedback loop has these symptoms:

- OTLP requests continue while the application is idle.
- Export batches contain only networking diagnostics.
- Request volume increases after enabling `DEBUG` or `TRACE`.

See [issue #2877] for ongoing discussion.
